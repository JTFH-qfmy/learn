# 扩展与维护说明

## 按需要长出内容

1. **先完成一条记录。** 从 [PGC 仿真](../pgc-simulation/README.md)或当前正在学习的问题开始，复制模板，保存可运行的最小实验。
2. **有文件再建子目录。** 一个实验可逐步增加 `src/`、`data/`、`figures/` 和 `results/`；这些名称是建议，不必预先创建空目录。
3. **有脚本再固定依赖。** 将依赖版本及安装、运行方式放在具体实验目录；例如 Python 项目需要时再增加自己的依赖文件。LabVIEW 项目写明所需版本与工具包，并随项目保存必要子 VI。
4. **有重复步骤再自动化。** 先手动验证，再添加小脚本；出现持续维护需求后才考虑测试、自动检查或文档站点。
5. **有重复实现再抽公共模块。** 保留原实验的版本引用和运行方式，避免公共代码变化让旧记录失去复现条件。

## 数据与结果

- 原始输入与处理结果分开保存，不用处理结果覆盖原始输入。
- 每轮实验使用独立运行编号，保存对应参数；复现所依赖的小型数据或基准结果可以提交。
- 大型波形、采集文件和批量输出按需要放外部存储。在记录中保留稳定位置、获取方法、文件名、大小、访问条件和 SHA-256；文件校验在 Windows 可用 `Get-FileHash -Algorithm SHA256 -LiteralPath '<文件路径>'`。
- LabVIEW 源文件通常无法像文本一样直接比较，提交时用文字说明 VI 的关键变更，并保留必要截图；截图不能代替源文件。
- 不按扩展名全局忽略 CSV、MAT、TDMS 或 VI 等科研文件；是否提交取决于大小、公开权限及复现需要。

## 提交与回看

- 每次提交聚焦一个问题，提交说明写清改变和目的，例如 `docs(pgc): record baseline simulation steps`。
- 运行记录引用实际使用的代码提交；若记录和代码同时首次提交，可在后续记录中补充该提交 SHA，无需让文件引用包含自身的提交。
- 一项记录至少能回答：做了什么、用什么版本和输入、如何重跑、结果在哪里、还有什么未解决。
- 纠错时保留原观察，注明更正原因；不要把失败结果改写成成功。
- 实验较多时再给各主题补充索引；需要协作或跟踪长期问题时再使用 Issue 与 PR。

## 当前边界

首版仅含说明、模板和基础文件规则。没有预装依赖、自动流水线、硬件控制程序或仿真实现。后续工具由真实实验需要决定；如需许可协议，再根据自己拥有权利的代码、文字与数据分别确认授权范围。
